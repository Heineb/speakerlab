# Current Beocreate SigmaTCP Contract

## Evidence and confidence

This contract characterizes `beocreate_essentials/dsp.js`. The repository contains no captured physical SigmaTCP exchange, SigmaTCP server source or protocol specification. Request bytes generated by current code are therefore **verified current-code behavior**. Response layout is **strongly evidenced** by the current decoder but is not a verified physical capture.

Golden fixtures are in `test/fixtures/sigmatcp-golden.json`. Synthetic invalid and response fixtures are labelled as such.

## Connection and framing

- TCP, default host `127.0.1.1`, fixed port 8086.
- Fourteen-byte header; byte 0 is the command.
- Parameter write command is `0x09`; parameter read is `0x0a`.
- All multi-byte parameter fields and payload values are big-endian.
- A read request has no payload: requested byte count is header bytes 8–9 and address is bytes 10–11.
- A write request stores total frame length in byte 6, payload length in bytes 10–11, address in bytes 12–13, then payload.
- The current write generator only represents total lengths up to 255 in byte 6. No deliberate maximum or backpressure policy is present.
- The current read-response decoder uses bytes 8–9 as payload length, bytes 10–11 as address and payload from byte 14. It does not validate command, available length, trailing bytes or partial frames.
- No repository evidence defines an error-response format, unsolicited parameter messages or a write acknowledgement frame.

Current `onData` assumes one complete logical response in each Node socket `data` event except for a special XML accumulator. Parameter frames split across reads or coalesced into one read are not handled safely. Malformed or truncated parameter data may decode zeros/undefined values or throw. There is no parameter-frame completion timeout or input-buffer bound.

`sigmatcp-protocol.js` is an isolated future-boundary parser. It retains incomplete frames, emits coalesced frames, validates lengths and commands, bounds buffering, enters a deterministic error state and requires explicit reset. Production `dsp.js` is unchanged.

## Correlation and read queue

The wire format has no request identifier. Current correlation is by returned parameter address and `openReadRequests[address]`. The local queue sends one parameter read at a time. Multi-read is implemented as several serialized single-address reads.

Consequences:

- two outstanding reads for the same address are not supported at once;
- there is no parameter-read timeout, cancellation or shutdown cleanup;
- malformed/no response leaves the open request indefinitely and prevents the queue advancing;
- disconnect/reconnect does not clear pending reads or the queue;
- a late response can satisfy an old address entry after reconnect;
- callbacks are not guaranteed exactly once under malformed/duplicate transport input;
- `multiReads` IDs are address concatenations and can collide for different address lists;
- XML and checksum each use one global callback, so concurrent calls overwrite it.

The isolated transport simulator uses positional single-outstanding correlation plus a socket generation. Timeout, disconnect and shutdown complete callbacks exactly once, clear queued work and reject stale old-generation responses. This is a future deployment requirement, not a claim about production behavior.

## Writes and acknowledgement

`writeDSP`, `writeRegister` and software safeload are synchronous fire-and-forget wrappers around `socket.write()`. They return `false` only when already considered disconnected; otherwise they return `undefined`. Node `socket.write()` backpressure is ignored. Asynchronous errors and disconnect immediately after enqueue cannot be attributed to an operation.

No write acknowledgement is parsed. Successful method return means only that code attempted to enqueue bytes on the local TCP socket; it does not mean accepted, written to the DSP, applied, audible or durable. Future application requires explicit readback.

Software safeload sends ordinary writes to parameter addresses 24576 onward, then target address 24581 and word count 24582. Current code does not acknowledge the batch atomically or detect interruption between those writes.

## Reconnect and timeouts

After close, the current wrapper waits 2,000 ms and retries up to 10 times without backoff. Success resets the counter. Manual disconnect disables keep-alive. There is no explicit connection, parameter-read, frame, write-acknowledgement, deployment or reconnect-attempt timeout.

XML has a 10,000 ms timeout. DSP Programs independently times checksum acquisition at 5,000 ms, but the lower-level callback remains installed. Pending parameter work is neither failed nor replayed deliberately. Program identity is not automatically rechecked for deployment.

Future deployment must invalidate pending work, cached readback and the compiled target on disconnect; use a new socket generation; reacquire identity; and never resume an interrupted deployment automatically.

## Other commands

Current code defines checksum request/response `0xf1/0xf2` and XML request/response `0xf4/0xf5`. XML is accumulated using its declared length, but split-header, overrun and coalesced-message cases are not handled. Unknown parameter commands fall through to the decoder. Idle timeout and server close semantics are not established by repository evidence.
